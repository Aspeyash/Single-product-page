==============================================================================
ZYMARG DESIGN TOKENS
==============================================================================

Brand primary is #9500A5.
Every purple in every ZYMARG surface resolves to this value or to its
gradient siblings #BD00D1 and #FEA9FF.

  PART 1   FRONT END DESIGN     everything the public sees
  PART 2   BACK END DESIGN      every wp-admin screen
  PART 3   DISCOVERY SPARK      the brand mark and the only loading indicator


HOW TO USE THIS DOCUMENT
---------------------------------------------------------------------------

Every value in the brand has exactly ONE name. That name is the same in the
front end and in the back end. Parts 1 and 2 list the values with their
names; the full token file is in the section below.

Do not invent a second name for a value that already has one. Do not write a
raw colour or size inside a rule. If a value is not in this document, it is
not in the brand.

The front end and the back end differ only in WHERE the tokens are declared,
and in a small set of deliberate overrides listed in section 2.9.

Part 3 is literal code. The Discovery Spark must be pixel-identical
everywhere, so it is copied, never adapted.


THE SHARED FILES
---------------------------------------------------------------------------

Three files are shared by every ZYMARG plugin. Each is enqueued with the
SAME handle in every plugin, so WordPress loads each one only once no matter
how many plugins are active.

File                  Handle            Contains
---------------------------------------------------------------------------
zymarg-tokens.css     zymarg-tokens     Every --zym-* value
zymarg-spark.css      zymarg-spark      The Discovery Spark
<your plugin>.css     per plugin        Only that plugin's own layout

Rules

1.  The handle must be spelled identically in every plugin. WordPress
    deduplicates by handle, so a mismatch means two copies load and the
    later one silently wins for every plugin on the page.
2.  Version the shared files independently of any plugin. Bump the token
    file version only when a token actually changes, not on every plugin
    release.
3.  The shared files are append-only in practice. Add tokens freely. Never
    change or remove an existing value without shipping every plugin
    together, or an out-of-date plugin will override the new value.
4.  A plugin's own stylesheet declares zymarg-tokens as a dependency so the
    tokens are always loaded first.
5.  A plugin never redefines a --zym-* value. If a plugin needs something
    the brand does not have, it belongs in this document first.

Debug markers

The token file carries its own version and the slug of the plugin that
shipped the copy that won:

  --zym-tokens-version: "2.2.0";
  --zym-tokens-owner:   "zymarg-homepage";

When a page looks wrong, one line in the browser console tells you which
copy the browser actually used:

  getComputedStyle(document.documentElement).getPropertyValue('--zym-tokens-owner')

Use a custom property for this, not a comment banner. Comment banners are
stripped by minifiers; custom properties survive.

1.1a  FIXED TOKENS  -  TEXT AND SURFACES THAT SIT ON THE GRADIENT
---------------------------------------------------------------------------

Added in token file v2.2.0. These three are FIXED: their value never
changes in dark mode, unlike every other colour in 1.1. Declared once in
the shared block (both systems), not duplicated in the dark-mode block.

Name                Token                          Value      Used for
---------------------------------------------------------------------------
On gradient         --zym-color-on-gradient        #FFFFFF    Text and
                                                              icons drawn
                                                              directly on
                                                              --zym-gradient,
                                                              or on any
                                                              other fully
                                                              saturated
                                                              brand fill
Primary fixed       --zym-color-primary-fixed      #FFD6FB    A permanently
                                                              light pink
                                                              tint: emphasis
                                                              text sitting
                                                              on the
                                                              gradient,
                                                              plus fixed
                                                              light chips,
                                                              rings or pills
                                                              that must not
                                                              react to dark
                                                              mode
On primary fixed    --zym-color-on-primary-fixed   #36003D    Text or icons
                                                              placed ON TOP
                                                              of a
                                                              --zym-color-
                                                              primary-fixed
                                                              surface

Why these exist: --zym-gradient is deliberately identical in light and dark
mode (see 1.2 and the dark-mode block header comment: "the mark should read
the same in both modes"). But nothing in the ORIGINAL token set named the
text/icon colour that sits on top of it, so every plugin either hardcoded
raw #fff (breaking rule 13 in 1.13 / rule 5 in 2.10, "no raw colour inside a
rule") or aliased it to a theme-reactive token such as --zym-color-surface —
which flips to a near-black value in dark mode and produces illegible
dark-on-gradient text the moment a visitor switches themes. These three
tokens close that gap with names, not raw values.

When to use which:

  Is the element sitting directly on --zym-gradient (or another fully
  saturated brand fill, e.g. a solid --zym-color-primary button)?
    -> Primary text/icon on it:      --zym-color-on-gradient   (#FFFFFF)
    -> Secondary/muted text on it,
       or a fixed light chip/ring
       that must ignore dark mode:   --zym-color-primary-fixed (#FFD6FB)

  Is the element sitting on a --zym-color-primary-fixed surface (the pink
  chip/ring itself), not on the gradient directly?
    -> Text/icon on that surface:    --zym-color-on-primary-fixed (#36003D)

Never substitute --zym-color-surface or --zym-color-text for any of the
three above. Those two DO react to dark mode; the fixed trio does not, by
design, because the gradient behind them does not either.

2.10  RULES
---------------------------------------------------------------------------

1.  Scope every back end rule to the plugin's admin wrapper.
2.  Never declare back end tokens at document root.
3.  Never redefine a --zym-* value inside a plugin. If you need something the
    brand does not have, add it to this document first.
4.  Class naming is BEM with one short prefix per plugin. Class prefixes are
    per plugin; token names are not.
5.  No raw colour or size inside a rule. Reference the token.
6.  No inline styles in templates.
7.  No forced overrides, except to reassert a value over a WordPress core
    style. When you must, leave a comment naming the core rule you are
    beating.
8.  Focus styling applies to keyboard focus only, using --zym-focus-ring.
    Never remove focus styling without replacing it.
9.  Never signal state with colour alone. Pair it with a label, icon or text.
10. Interactive targets are at least 32x32.
11. Icon-only buttons carry an accessible label. Decorative graphics are
    hidden from assistive technology.



2.11  WORDPRESS CORE PRIMITIVES
---------------------------------------------------------------------------

A wp-admin screen is never all ZYMARG markup. Half of a typical settings
screen is markup that WordPress itself emits: form_table rows, submit
buttons, descriptions, notices, native checkboxes. That markup carries NO
ZYMARG class, so nothing in 2.8 reaches it.

This is the most common way a screen fails.

  Removing hardcoded colour from a screen does not brand it.
  It hands the screen back to the wp-admin defaults.

A screen can contain zero inline styles and zero raw hex and still render
as stock WordPress grey with a blue primary button. Every primitive below
must be branded, scoped to the plugin's admin wrapper. These are the
sanctioned exception to rule 7 in 2.10: you are reasserting a value over a
WordPress core style, so leave the comment that rule asks for.

Primitive                     Treatment
---------------------------------------------------------------------------
table.form-table              Card per 2.8: surface, 1px border,
                              --zym-radius-card, --zym-shadow-surface,
                              22px 24px padding
.form-table th                Label: 13px, 600, --zym-color-dark, top
                              aligned
.form-table td                14px, --zym-color-text
p.description                 13px, --zym-color-neutral-text, 6px top
                              margin. Never the core italic grey.
input[type=text], [email],    TEXT INPUT per 2.8: surface, 1px border,
[url], [password],            --zym-radius-control, 10px 12px, 14px.
[number], [search],           Focus: border --zym-color-primary plus
textarea, select              --zym-focus-ring
input[type=checkbox],         18x18, accent-color --zym-color-primary,

                              dashicon tick -- replace it, do not tint it.

                              WordPress blue; it is never left as-is.

2.12  SCREEN ACCEPTANCE CHECKLIST
---------------------------------------------------------------------------

A screen is not done because it was written against this document. It is
done when it passes this list.

  WARNING. "No inline styles and no raw hex" is necessary but NOT
  sufficient. It measures code cleanliness, not brand compliance. A screen
  can pass both and still be entirely off-brand. Never use it alone as the
  definition of done.

Structure
  1.  Header matches the reference in 2.14 exactly: Spark, wordmark,
      subtitle, version badge.
  2.  The Spark is present and animating. A static Spark is a bug.
  3.  No spinner anywhere on the screen or in its JavaScript.
  4.  No full-bleed gradient bar.

Coverage
  5.  List every WordPress core primitive the screen renders and confirm
      each one is branded per 2.11. Do this by reading the rendered page,
      not the source.
  6.  Every component matches its 2.8 definition in shape, not only in
      colour.

Code
  7.  Every rule scoped to the plugin's admin wrapper. Nothing at document
      root.
  8.  No inline style attributes and no <style> blocks.
  9.  No raw colour or size inside any rule.
  10. Every var(--zym-*) used resolves against the token file. Diff the
      names you used against the names defined; do not eyeball it.

Accessibility
  11. Keyboard focus visible on every interactive element.
  12. No state signalled by colour alone.
  13. Interactive targets at least 32x32; icon-only buttons labelled.
  14. prefers-reduced-motion respected, including the Spark.

Integration
  15. Viewed side by side with an existing compliant screen. If it looks
      like a different product, it is.
  16. Tested with a second ZYMARG plugin active, to prove the shared
      handles deduplicate.
  17. Tested with the zymarg-os theme both active and inactive, to prove
      the Spark delegation in 3.9 falls back correctly.



2.13  RETROFITTING AN EXISTING SCREEN
---------------------------------------------------------------------------

This document reads as though every screen is new. Most are not. Converting
an existing screen fails in its own particular way:

  Swapping hex values for tokens recolours a component.
  It does not rebuild it.

The result is a screen that passes every code check while keeping the wrong
shape, the wrong header and the wrong proportions.

  If a retrofitted screen looks essentially unchanged, the retrofit has not
  happened yet. A correct retrofit is visibly different.

Order of work

  1.  Inventory. List every component on the screen and every core
      primitive from 2.11 that it renders.
  2.  Replace the header with the reference in 2.14. Do not adapt the old
      one.
  3.  Rebuild each component to its 2.8 definition, shape first.
  4.  Brand every core primitive per 2.11.
  5.  Remove inline styles and <style> blocks last, once the classes that
      replace them exist.
  6.  Run 2.12.

Step 5 is last on purpose. Stripping inline styles first leaves the screen
relying on wp-admin defaults, which looks worse than where you started and
hides what still needs doing.

2.15  ENVIRONMENT SUPPORT
---------------------------------------------------------------------------

BROWSER BASELINE

  The last two major versions of Chrome, Edge, Firefox and Safari.

  Allowed without a fallback:
    custom properties, color-mix(), clamp(), :is(), :where(), flex gap,
    inset shorthand, accent-color

  Not allowed without a fallback:
    native CSS nesting, @container, :has() where it carries layout

  color-mix() is the sanctioned way to derive a translucent or tinted
  variant of an existing token, for example a white overlay on the
  gradient. Deriving from a token is not the same as inventing one, and
  does not breach rule 3 in 2.10. Never hand-write the resulting rgba.

WP-ADMIN COLOUR SCHEMES

  Users can change their admin colour scheme in their profile. Default,
  Light, Midnight, Ectoplasm and the rest all repaint WordPress chrome.

  ZYMARG screens do not adapt to the scheme. Everything inside the plugin
  wrapper is brand-coloured and self-contained, so it looks the same on
  every scheme. Two things sit OUTSIDE the wrapper and will change:

    - the admin sidebar, including the plugin's own menu highlight
    - core notices rendered above the wrapper

  Never depend on a core scheme colour for contrast. Test each screen on
  Default and on Midnight, which are the two extremes.

DIRECTION

  Prefer logical properties -- margin-inline, padding-inline, inset-inline
  -- over left and right, so screens survive an RTL locale.



==============================================================================
PART 3  -  DISCOVERY SPARK
==============================================================================

The ZYMARG Discovery Spark is the brand mark. It has two jobs:

  1.  The logo, in every admin header and wherever the brand mark appears.
  2.  THE LOADING INDICATOR, everywhere, on both the front end and the
      back end.

It lives in one shared file, zymarg-spark.css, enqueued with the handle
zymarg-spark. It is never copied into a plugin and never renamed. The class
names below are brand identity, not plugin styling, so the per-plugin class
prefix rule does NOT apply to them.


3.1  THE NO SPINNER RULE
---------------------------------------------------------------------------

  ZYMARG DOES NOT USE LOADING SPINNERS.

Not allowed, anywhere, on any surface:

  - Rotating rings or arcs
  - CSS border spinners
  - Bouncing or pulsing dots
  - The WordPress core .spinner element
  - Any spinner shipped by a third-party library or theme

Wherever a loading state is needed, render the Discovery Spark instead. Its
sequential lens pulse IS the loading animation. It already loops infinitely,
so nothing needs to be added to it.

Why: the Spark is the only motion in the brand. A generic spinner beside it
makes the product look assembled from parts rather than designed. The Spark
also earns brand recall during the exact moment the user is forced to wait.

There is no spinner token anywhere in this system. If you find one in a
codebase it is a leftover and must be removed.

When auditing, search for the word "spinner", not just for a CSS custom
property name. Spinner definitions hide in PHP constants and JavaScript as
well as in stylesheets.


3.2  ANATOMY
---------------------------------------------------------------------------

A 24x24 viewBox SVG containing three groups, drawn back to front:

  accent      the small lens, top left
  companion   the medium lens, lower left
  hero        the large lens, right

Each group holds two shapes: a purple lens and a gold core.
The purple lenses animate. The gold cores never animate.

Colours
  Lens purple   --zym-color-primary      #9500A5
  Gold core     --zym-spark-gold         #FFD166
  Glow          rgba(149, 0, 165, 0.25)

The lens reads the brand primary token, so recolouring the brand recolours
the Spark. The glow is expressed as the same RGB triplet in one variable, so
the fill and the glow cannot drift apart.


3.3  SIZE MATRIX
---------------------------------------------------------------------------

Class                   Offset     Size
---------------------------------------------------------------------------
.zymarg-spark--sm       0.55px     20px     inside a button
.zymarg-spark--md       0.70px     24px     default inline and loading size
.zymarg-spark--lg       0.90px     32px     panel or card
.zymarg-spark--xl       1.20px     48px     full page or modal
.zymarg-spark--xxl      1.50px     60px     splash and marketing

between lg and xl.

The offset exists because the purple lenses are drawn slightly up and left
of the gold cores; the translate re-centres them. The offset MUST scale with
the size or the two layers visibly separate.

Always size the Spark with a size class. Never with a transform scale, which
leaves the offset behind.

3.7  RULES
---------------------------------------------------------------------------

1.  Never use a spinner. The Spark is the only loading indicator.
2.  One shared file, one handle. Never copy the Spark into a plugin and
    never rename its classes. Two copies is how the fill and the glow drift
    apart.
3.  A static Spark is a bug. In the admin header and in every loading state
    it must be animating.
4.  Never place the Spark on a coloured or gradient background. It needs
    white or a light tint to read.
5.  Never size it with a transform scale. Use a size class.
6.  Never speed it up or slow it down to suggest progress. If you need
    progress, use a progress bar with the gradient fill and leave the Spark
    out of it.
7.  One Spark per loading region. Do not put a Spark in every skeleton row.
8.  In the admin header it renders at 44x44 directly on white, with no
    container, no chip and no letter mark beside it.
9.  Never animate the gold cores.
10. The Spark's reduced-motion rule must come after any global
    reduced-motion block, or the global rule wins and the Spark keeps
    animating.


3.8  UPSTREAM WARNING
---------------------------------------------------------------------------

The mark originates from the Discovery Spark package. That package ships the
lens purple as #6833EA, a blue-violet roughly 37 degrees off the brand hue,
and hardcodes the same value into the drop-shadow glow.

If you pull or update from upstream you MUST recolour both:

  lens fill   #6833EA      ->  #9500A5
  glow        104, 51, 234 ->  149, 0, 165

Recolouring only the fill and leaving the glow behind is the common mistake.
The stylesheet above avoids it by reading the fill from --zym-color-primary
and keeping the glow in a single variable. Pin any upstream change with a
comment so the next update does not silently revert it.



3.9  NAMING -- THE REDECLARE HAZARD
---------------------------------------------------------------------------

Read this before writing any PHP that touches the Spark. Getting it wrong
takes the whole site down, not just a screen.

The zymarg-os THEME declares these functions WITHOUT a function_exists
guard:

  zymarg_discovery_spark()    inc/discovery-spark.php
  zymarg_loading()

Plugins load BEFORE the theme. So if a plugin declares either name, the
plugin's definition lands first, and then the theme's bare declaration
fatals the site:

  Fatal error: Cannot redeclare zymarg_discovery_spark()

  A function_exists guard on the PLUGIN side does not prevent this. The
  guard protects the declaration it wraps. The unguarded declaration is the
  theme's, and it is the one that fatals.

Rules

  1.  A plugin NEVER declares a shared ZYMARG global name. Every global
      function a plugin declares carries that plugin's own prefix:
      zymarg_vd_ for Vendor Dashboard, zymarg_sp_ for Store Page.
  2.  Reach the Spark through a prefixed wrapper that delegates in order:
      the theme's helper if it exists, then another ZYMARG plugin's
      wrapper, then a local fallback copy.
  3.  Stylesheet HANDLES are the opposite case. WordPress deduplicates
      styles by handle, so handles stay shared and identical across every
      plugin, guarded with wp_style_is(). Shared handles, prefixed
      functions.
  4.  Never "simplify" a prefixed wrapper back to the shared name. It will
      look like harmless cleanup and it will fatal the site.

The delegation pattern

  function zymarg_xx_spark( $args = array() ) {
      // The theme owns the mark. Hand off whenever it is loaded.
      if ( function_exists( 'zymarg_discovery_spark' ) ) {
          return zymarg_discovery_spark( $args );
      }
      // Then any sibling ZYMARG plugin.
      if ( function_exists( 'zymarg_vd_spark' ) ) {
          return zymarg_vd_spark( $args );
      }
      // Then the local fallback copy.
      return zymarg_xx_spark_fallback( $args );
  }

Before shipping, scan the plugin and confirm every global function it
declares carries the plugin prefix:

  grep -rhoE '^\s*function\s+[a-zA-Z0-9_]+' --include='*.php' .
